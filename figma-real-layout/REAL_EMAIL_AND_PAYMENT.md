# Подключение реальной почты и оплаты

## Что уже готово

- Экраны регистрации, входа, подтверждения почты и восстановления пароля сверстаны по странице Figma «Верстка 3».
- Реализован Node.js/Fastify backend для регистрации, входа, восстановления пароля и HttpOnly-сессий.
- Код `111111` и локальные аккаунты удалены; одноразовые коды генерируются сервером и отправляются через SMTP Яндекса (Resend сохранён как резервный транспорт).
- Телефон из авторизации убран: идентификатором пользователя является email.

Для реальной доставки писем требуется настроить домен отправителя и задать реквизиты почтового сервиса на сервере. Без них API не имитирует отправку и возвращает понятную ошибку. Для оплаты реализован серверный контур Точки: создание ссылки, проверка статуса и однократное начисление после `APPROVED`. Боевой запуск блокируется, пока JWT не получит права интернет-эквайринга и не будет известен `merchantId`.

## Что запросить у владельца проекта

Передавать секреты нужно через менеджер паролей или зашифрованный архив, не через чат и не через Git.

### Для почты

1. Домен сайта и доступ к его DNS.
2. Адрес отправителя, например `no-reply@domain.ru`.
3. Отображаемое имя отправителя, например «Битва игр».
4. Для Яндекс 360 — отдельный служебный ящик и пароль приложения для SMTP; пароль от личного аккаунта не нужен.
5. Доступ для добавления MX, SPF, DKIM и DMARC-записей домена.
6. Адрес для ответов пользователей и контакты техподдержки.

### Для оплаты

Интеграция рассчитана на интернет-эквайринг Точки.

1. JWT приложения Точки с разрешениями `ReadAcquiringData` и `MakeAcquiringOperation`.
2. `customerCode` и активный `merchantId` торговой точки со статусом `REG`/`isActive=true`.
3. Юридический статус продавца: ООО, ИП или самозанятый.
4. Данные для чеков: система налогообложения, ставка НДС, предмет и способ расчета. Их должен подтвердить бухгалтер.
5. Решение для онлайн-кассы или подключенная к Точке касса.
6. Наименование товара в чеке, например «Индивидуальные бланки, категория …, 30 шт.».
7. Утвержденные цены и правила начисления бланков.
8. Email поддержки, ссылка на оферту, политику конфиденциальности и правила возврата.

## Необходимая серверная часть

Текущий минимальный контур: Node.js/Fastify API + атомарное файловое хранилище на одном VPS + HTTPS. Фронтенд обращается только к `/api`; почтовые реквизиты, JWT Точки и ключ сессий хранятся только на сервере в переменных окружения. При переходе на несколько серверных процессов файловое хранилище нужно заменить PostgreSQL.

### Таблицы

- `users`: id, name, email, password_hash, email_verified_at, created_at.
- `verification_codes`: user/email, purpose, code_hash, expires_at, used_at, attempts.
- `sessions`: user_id, token_hash, expires_at, revoked_at.
- `orders`: user_id, category_id, quantity, amount, currency, status.
- `payments`: order_id, provider_payment_id, status, amount, payload, processed_at.
- `purchases`: user_id, order_id, category_id, blanks_count, created_at.

Email в базе должен быть нормализован и иметь уникальный индекс.

### API авторизации

- `POST /api/auth/register` — создать неподтвержденного пользователя, отправить код.
- `POST /api/auth/verify-code` — подтвердить регистрацию или вход по коду.
- `POST /api/auth/login` — вход по email и паролю.
- `POST /api/auth/login-code` — запросить код для входа без пароля.
- `POST /api/auth/forgot-password` — запросить код восстановления.
- `POST /api/auth/reset-password` — проверить код и записать новый хеш пароля.
- `POST /api/auth/logout` — отозвать сессию.
- `GET /api/me` — получить текущего пользователя.

### Защита авторизации

- Пароли хешировать на сервере через `scrypt` с уникальной солью; исходный пароль не сохранять.
- Коды хранить только в виде хеша, срок жизни — около 10 минут, использовать один раз.
- Ограничить отправку кодов и попытки ввода, например 1 письмо в минуту и 5 писем в час.
- Не сообщать незнакомому пользователю, зарегистрирован ли конкретный email, если это не требуется согласованным дизайном.
- Сессию хранить в cookie `HttpOnly; Secure; SameSite=Lax`, а не в `localStorage`.
- Добавить журналирование входов, восстановлений и блокировок без записи паролей и кодов.

`DEMO_AUTH_CODE`, уведомления «Демо-код: 111111» и локальное хранение аккаунтов уже удалены.

## Сценарий отправки письма

1. Сервер генерирует криптографически случайный одноразовый код.
2. Сохраняет только хеш кода и срок действия.
3. Отправляет письмо через защищённое SMTP-соединение с кодом, сроком действия и пометкой «Если это были не вы, проигнорируйте письмо».
4. После успешной проверки помечает код использованным.
5. Для регистрации заполняет `email_verified_at`; для восстановления разрешает ровно одну смену пароля.

Перед запуском проверить доставку на Яндекс, Mail.ru, Gmail и корпоративные адреса, а также SPF/DKIM и попадание письма не в спам.

## Сценарий оплаты через Точку

1. Фронтенд отправляет серверу только идентификатор категории и количество бланков.
2. Сервер сам берет цену из каталога, создает заказ со статусом `pending` и не доверяет сумме из браузера.
3. Сервер создаёт ссылку через `POST /acquiring/v1.0/payments`; JWT никогда не попадает во frontend.
4. В `paymentLinkId` передаётся внутренний номер платежа, а в `redirectUrl` — HTTPS-страница возврата сайта.
5. Браузер переходит на `paymentLink`, полученный от Точки.
6. Возврат пользователя на `return_url` сам по себе не означает успешную оплату.
7. Сервер запрашивает `GET /acquiring/v1.0/payments/{operationId}` и сверяет operationId, сумму, customerCode, merchantId и paymentLinkId.
8. В одной атомарной операции сервер помечает заказ оплаченным и начисляет баланс. Повторная проверка не начисляет его второй раз.
9. После этого покупка появляется в личном кабинете.

Для мгновенного фонового подтверждения дополнительно подключается webhook Точки `acquiringInternetPayment`; текущий возврат пользователя уже перепроверяется через API и сам по себе оплатой не считается.

## Чеки

Электронная квитанция платежного сервиса не заменяет кассовый чек. До запуска бухгалтер должен определить схему применения 54-ФЗ и значения `vat_code`, `payment_subject` и `payment_mode`. Эти значения нельзя угадывать в коде.

## Серверные переменные окружения

Пример названий без реальных значений:

```env
AUTH_SECRET=
AUTH_DATA_FILE=server-data/auth.json
APP_ORIGIN=https://example.ru

EMAIL_FROM="Битва Игры <support@muzlotodoma.ru>"
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=support@muzlotodoma.ru
SMTP_PASSWORD=<пароль приложения Яндекс Почты>

# Необязательный резервный транспорт
RESEND_API_KEY=

TOCHKA_API_BASE_URL=https://enter.tochka.com/uapi
TOCHKA_JWT_TOKEN=
TOCHKA_CUSTOMER_CODE=
TOCHKA_MERCHANT_ID=
TOCHKA_PAYMENT_MODES=card,sbp
TOCHKA_RETURN_URL=https://example.ru/#/balance-top-up
TOCHKA_FAIL_RETURN_URL=https://example.ru/#/balance-top-up
```

Эти переменные нельзя называть с префиксом `VITE_`: все `VITE_*` попадают в клиентскую сборку и доступны посетителю сайта.

## Порядок внедрения и приемки

1. Серверный API и фронтенд уже связаны; прогнать автотесты.
2. Подключить SMTP Яндекса и проверить все четыре сценария: регистрация, повторная отправка, вход по коду, восстановление пароля.
4. Выдать JWT Точки права интернет-эквайринга, получить merchantId и подключить webhook.
5. Прогнать успешную, отмененную, повторную и зависшую оплату, повтор webhook и несовпадение суммы.
6. Проверить чек и начисление ровно одной покупки.
7. Провести приемку на мобильных и десктопных браузерах.
8. Только после этого заменить тестовые реквизиты боевыми, удалить демо-код и очистить тестовые заказы.
